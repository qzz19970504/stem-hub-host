# 控制台布局与接收缓存优化设计

## 背景与目标

当前控制台页存在三类问题：

1. 电机卡和输出卡的分隔线不在同一水平位置，上方内容也没有在各自区域内形成一致的垂直留白。
2. AT 日志只能持续追加，缺少右键清空入口。
3. 图表数据保留 5 分钟，AT 日志的 Python 条目列表和 Qt 文档均无上限，长时间运行会持续增加内存占用。

本次修改只涉及上位机。COM12 用于真实硬件的只读连接、查询和持续接收验证，不发送控制输出，不刷写或改动固件。

## 布局设计

电机卡与输出卡采用共享的“上部内容区高度”设计令牌。两张卡的分隔线放在该内容区之后，因此在相同卡片高度下具有一致的全局纵坐标。

- 电机卡上部内容区包含 MODE 和 CURRENT，两者作为一个内容组放在上下弹性间距之间。
- 输出卡上部内容区包含五个开关和 ALL OFF，整体作为一个内容组放在上下弹性间距之间。
- 两个内容组使用统一的最小上下留白令牌，避免内容贴近卡片顶部或分隔线。
- 分隔线以下区域保持现有电机按钮和故障指示器行为，不改变协议或控制语义。

几何回归测试在固定卡片尺寸下检查：

- 两张卡分隔线的 `y` 坐标一致，允许最多 1 像素渲染误差。
- 两个上部内容组的中心与共享上部内容区中心一致，允许最多 2 像素布局误差。
- 内容组顶部和底部均满足共享最小留白。

## AT 日志右键菜单

AT 日志视图使用自定义上下文菜单，包含“清除全部”动作。

该动作：

- 清空可见日志文档。
- 清空内存中的日志条目及其时间戳。
- 不发送串口命令。
- 不清空图表数据。
- 不修改命令输入框。

日志视图原有的复制、选择能力保持可用；在存在选中文本时，菜单保留“复制”动作。

## 接收数据保留策略

统一采用最近 180 秒的滚动窗口，并增加条目数硬上限作为异常流量保护。

### 图表数据

- `DataBuffer.WINDOW_SECONDS` 从 300 秒改为 180 秒。
- 每个通道继续在新样本进入时按时间淘汰过期数据。
- `deque.maxlen` 保留为额外防护，容量调整为足以覆盖正常采样率且不会无限增长的值。

### AT 日志

- 每条日志记录单调时钟时间戳。
- 新日志到达时淘汰 180 秒以前的记录。
- 同时设置最大日志条目数，防止异常高频串口流量在 180 秒内占用过多内存。
- Qt 文档块数同步设置硬上限，避免 Python 列表已受限但底层文本布局仍持续增长。
- 当时间淘汰导致历史记录变化时，以受限条目集重建文档，保证可见内容和内存记录一致。
- 主题切换后的日志重绘仍只使用当前受限条目集。

## 错误处理与兼容性

- 日志清空和淘汰均为本地 UI 操作，不触及串口状态机。
- 保留现有 `append_log`、`append_info` 和 `append_error` 公共调用方式。
- 现有图表清空功能继续调用 `DataBuffer.reset()`。
- 深色和浅色主题均使用现有菜单与文本颜色体系。

## 测试与验收

自动化测试覆盖：

- 分隔线对齐、上部内容组垂直居中及最小留白。
- 右键菜单包含“清除全部”，触发后仅清空日志。
- 日志的 180 秒淘汰、条目硬上限和 Qt 文档块上限。
- 图表数据的 180 秒滚动淘汰。
- 完整 pytest 套件和视觉回归。

运行验证覆盖：

- 使用 fake firmware 检查控制台布局、右键清空和持续接收。
- 使用 COM12 连接真实硬件，仅执行版本、传感器、故障及电机状态查询并观察持续接收。
- 运行发布构建，确认打包产物可启动。

## Git 流程

在 `codex/ui-console-memory-polish` 隔离分支中完成设计、实现和验证。全部测试通过后提交功能改动，合并回原始 `master`，再在合并结果上运行完整测试。
